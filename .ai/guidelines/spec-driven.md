# Spec-Driven Development (Spec Kit)

## When to Use

- Use the Spec Kit flow for new features: new domains, pages, endpoints, or user-facing behavior that needs requirements decided before code (e.g. note sharing, note expiration).
- Do not use it for small bug fixes, chores, dependency bumps, refactors, copy, or styling changes. Those go straight to the `tdd` skill (when behavior changes) and the `git-commit` skill.
- When in doubt, ask the user before starting the flow.

## Flow

Run the commands in order, one feature at a time. In Claude Code they are skills invoked with a hyphen (`/speckit-specify`); other agents may use the dotted form (`/speckit.specify`).

1. Create the branch first, following the Git Workflow guideline: `git switch -c feat/<slug>`.
2. `/speckit.specify <description>`: writes `specs/<NNN>-<slug>/spec.md` (what and why, no implementation). Optionally run `/speckit.clarify` to resolve open questions.
3. `/speckit.plan`: writes `plan.md` and design artifacts. The plan MUST follow the Architecture and Frontend guidelines (Form Request → Controller → Action, Policies, Wayfinder, shadcn-vue).
4. `/speckit.tasks`: writes `tasks.md`. Optionally run `/speckit.analyze` to check spec, plan, and tasks for consistency.
5. `/speckit.implement`: executes `tasks.md` (see below).
6. Open the PR with the `pull-request` skill. The `specs/<NNN>-<slug>/` folder is committed in the same PR as the feature.

## Implementation Rules

- `/speckit.implement` MUST follow the `tdd` skill: for every task that changes behavior, write one failing test first, show the red output, then write the minimum code to pass. A task list that puts tests after implementation does not override this.
- Code follows the Architecture, Frontend, Testing, and Language guidelines; the `new-feature` skill is the checklist for the backend and frontend pieces.
- A task is done only when the Definition of Done in the Testing guideline passes. Commit with the `git-commit` skill, one Conventional Commit per completed TDD cycle or small group of cycles.

## Branches and Spec Folders

- Branch names follow the Git Workflow guideline (`feat/<slug>`), never Spec Kit's `<NNN>-<slug>` format.
- Spec folders keep Spec Kit's `specs/<NNN>-<slug>/` format. The folder name is independent of the branch; Spec Kit tracks the active feature in `.specify/feature.json` (git-ignored), not in the branch name.
- Do not install the Spec Kit `git` extension: it creates `<NNN>-<slug>` branches and auto-commits, which conflicts with the Git Workflow guideline.

## Constitution

- `.specify/memory/constitution.md` references the guidelines in `.ai/guidelines/` (testing, architecture, frontend, language, git, and this file) instead of copying their rules. The guidelines are the single source of truth.
- When a rule changes, edit the guideline, not the constitution. If they ever conflict, the guideline wins.

## Generated Files

- `.specify/` and `.claude/skills/speckit-*/` are managed by the Specify CLI and versioned. Do not hand-edit them (the constitution changes only through `/speckit.constitution`); update them with `specify init --here --integration claude` (or the CLI's upgrade command) and review the diff.
- Other files in `.claude/` are generated by Boost and stay git-ignored.
